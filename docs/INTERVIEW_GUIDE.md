## 2. 项目介绍怎么说

> 所有数字必须是你自己测的，`【实测】` 处换成第 8 节测到的数据。

**30 秒版**：
> 我做过一个 RK3588 上的多路视频智能分析项目：同时接入 4 路视频，用 MPP 硬件解码、RGA 做图像处理、NPU 做目标检测，支持多模型结果融合，结果拼成一个画面显示，同时支持 RTMP、RTSP、GB28181 推流。我主要负责多线程架构、推理调度和推流部分。

**1 分钟版**：
> 项目跑在 RK3588 上，做 4 路视频的实时目标检测。每一路是一条独立的流水线：FFmpeg 拉流，MPP 硬件解码，RGA 转成 BGR，送到 NPU 推理。NPU 有三个核，我建了多个模型实例轮流绑到三个核上，多路同时推理。检测结果融合、画框后拼成一个画面，本地显示，同时编码推流。
>
> 工程上主要解决了三个问题：一是多线程解耦，拉流、解码、推理分开，压缩数据用有界队列、图像只保留最新帧，下游慢的时候延迟不会越积越多；二是实时性，目标帧率控制、跳帧推理，每一级都有明确的丢帧策略；三是稳定性，断流自动重连、推流断线重连、线程安全退出，用 ASan 查过内存泄漏。
>
> 在板子上 4 路 1080p 每路 `【实测】` fps，NPU 占用 `【实测】`，延迟约 `【实测】` 毫秒。

**边讲边画这张图**（面试时最有用的一张）：

```
 4 路视频 (文件 / RTSP 摄像头)
      |
 s1 拉流    FFmpeg 读压缩数据 ------------- 断流自动重连
      |     有界队列 (满了丢整组画面)
 s2 解码    MPP 硬件解码 -> NV12
 s3 转换    RGA 硬件转 BGR (零拷贝)
      |     最新帧缓冲 (只留最新一帧)
 s4 推理    NPU 检测, 实例绑 3 个核并行 ---- 跳帧推理、目标帧率
 s5 融合    多模型的框合并, 画框
      |     最新帧缓冲
 s6 输出    拼成 2x2 -> 显示 / 编码推流 (RTMP / RTSP / GB28181)
```

**被问"你负责哪部分"**：如实说。答不上来的地方，比硬撑更好的说法是："这块我参考了官方示例的用法，原理我理解的是……，细节回去再确认。"

## 3. 项目高频问题

### A. 架构与多线程（问得最多）

**A1 整体架构讲一下？有几个线程？**
每路一条独立流水线：拉流 → 解码 → 转换 → 推理 → 融合；各路结果交给拼接线程拼成一个画面，显示并推流。

```
 ch0: [拉流线程] -> 队列 -> [解码线程] -> 最新帧 -> [推理线程] --+
 ch1: [拉流线程] -> 队列 -> [解码线程] -> 最新帧 -> [推理线程] --+     模型实例池
 ch2: [拉流线程] -> 队列 -> [解码线程] -> 最新帧 -> [推理线程] --+-->  实例0 @ NPU核0
 ch3: [拉流线程] -> 队列 -> [解码线程] -> 最新帧 -> [推理线程] --+     实例1 @ NPU核1
                                                        |               实例2 @ NPU核2
                                                        v
                                 各路结果 -> [拼接线程] -> 主线程显示 / [推流线程] -> 网络
```

每路 3 个线程（4 路共 12 个），加上拼接线程、推流线程、主线程；多模型时还有一个推理线程池。

**A2 线程之间怎么通信？**
两种缓冲区，都是"互斥锁 + 条件变量"实现：

```
 BlockingQueue<T> (有界 FIFO, include/common/BlockingQueue.hpp)

   producer --push()--> [ p5 | p4 | p3 | p2 | p1 ] --pop()--> consumer
                         |<------ capacity ----->|
   push()    : 满了就等(背压)               -> 文件源用, 不丢数据
   tryPush() : 满了立即返回 false          -> 实时流用, 由调用方决定怎么丢
   close()   : 唤醒所有等待者, 之后 push 失败, pop 取完剩余后返回 false
```

```
 Mbuffer (单槽最新帧, include/common/Mbuffer.hpp)

   writer: write(f1)  write(f2)  write(f3)            <- 永不阻塞, 新帧直接覆盖
                 \        \         \
   slot:        [f1] ->  [f2]  ->  [f3]   seq: 1 -> 2 -> 3
                           ^
   reader: waitNew(after_seq=1) 拿到 f2; 若 f2 还没读就被 f3 覆盖 -> overwritten++
   peek(): 非阻塞拿当前最新(拼接/推流线程用, 可能重复拿到同一帧)
```

**A3 下游处理不过来怎么办？**
每一级都有丢帧策略，丢了多少都会计数：

| 位置 | 丢法 |
|---|---|
| 拉流 | 实时流队列满了，丢掉积压的整组画面，等下一个关键帧 |
| 解码后 | 推理没来得及取，新帧覆盖旧帧 |
| 推理前 | 超过目标帧率的帧直接丢 |
| 推理 | 每 N 帧推理一次，中间帧复用上次的结果 |

看哪一级开始丢帧，瓶颈就在它的下游。

**A4 多路抢 NPU，资源竞争怎么处理？会不会死锁？**
4 个推理线程共用 3 个模型实例，用"实例池"管理：

```
 空闲列表: [实例0(核0), 实例1(核1), 实例2(核2)]      <- 一把锁保护

 借: 加锁 -> 有空闲就拿走一个, 没有就在条件变量上睡着等 -> 解锁
 用: 用这个实例推理 (此时只有我在用)
 还: 加锁 -> 放回列表 -> 叫醒一个在等的线程 -> 解锁      (写在析构函数里, 出错也一定会还)
```

```
 时间(ms)   0          12         24         36
 核0:      [ch0 帧1 ] [ch3 帧1 ] [ch0 帧2 ] ...
 核1:      [ch1 帧1 ] [ch1 帧2 ] [ch3 帧2 ] ...
 核2:      [ch2 帧1 ] [ch2 帧2 ] [ch1 帧3 ] ...
 ch3:       等实例...   ^ ch0 归还后借到实例0
```

- **顺序**：路和路之间没有固定顺序，谁先借到谁先算；同一路内部严格按时间顺序。
- **不死锁**：线程池线程数 = 实例数，每个任务只借一个实例，借到后一定能算完归还，破坏了死锁的"占有并等待"条件。

**A5 线程池在项目里怎么用的？**
只在多模型时用。同一帧要跑 A、B 两个模型，推理线程把两个任务提交到线程池，拿到两个 `future`，两个模型在不同 NPU 核上同时算：

```
 单线程串行:   |--model0 12ms--|--model1 12ms--|              = 24ms
 线程池并发:   |--model0 12ms--|                                = ~13ms
               |--model1 12ms--|
```

单模型时不走线程池，推理线程直接算。

**A6 程序怎么安全退出？`std::thread` 析构会怎样？**
`std::thread` 析构时如果还没 join，会直接 `std::terminate`；线程里有没捕获的异常也会 terminate。我用 `WorkerThread` 封装：析构时 join，线程入口统一捕获异常。

```
 启动:  加载模型 -> 创建缓冲区 -> 启动 推流 -> 拼接 -> 推理 -> 解码 -> 拉流
        (最容易失败的先做)         (消费者先就绪, 生产者最后)

 退出:  1. 通知所有线程停止 + 关闭所有缓冲区 (叫醒所有正在等待的线程)
        2. 按 拉流 -> 解码 -> 推理 -> 拼接 -> 推流 的顺序 join
        3. 最后释放 NPU (确保已没有线程在用)

 另外: 信号处理函数只设一个原子标志; 忽略 SIGPIPE
```

**A7 为什么先加载模型、最后启动拉流？**
- 模型加载最容易失败，放在最前面，失败时还没有线程和网络连接，退出很干净；
- 消费者先启动、生产者最后，第一帧到来时下游都已准备好。

**A8 图像在多个线程之间传递怎么保证安全？**
约定"发布后不再修改"：解码线程每帧新建一个图像写入缓冲区，之后不再改它；只读的线程直接用；要修改的线程（推流时叠加时间）先拷贝一份再改。

### B. 音视频基础

**B1 I 帧、P 帧、B 帧、GOP、SPS/PPS？**
- I 帧：自己就能解码；
- P 帧：参考前面的帧；
- B 帧：参考前后的帧，压缩率高但延迟大，实时推流不用；
- GOP：两个 I 帧之间的一组画面；
- SPS/PPS：分辨率等解码参数，解码器必须先拿到。

**B2 为什么丢包要丢到下一个关键帧？**
P 帧依赖前面的帧，中间丢一个，后面整组都会花屏，直到下一个 I 帧：

```
 队列满(解码跟不上):
   queue: [P P P P P P ... P]  (64 个)      新来的包 tryPush 失败
   -> clear() 清空积压, drop.pkt += n
   -> wait_keyframe_ = true: 后续 P 帧全部丢弃, 直到下一个 I(IDR) 帧
   -> 从 I 帧重新开始喂解码器 -> 不花屏, 延迟被"截断"不再累积

 为什么不能只丢最老的一个包?  H.264 P 帧依赖前面的帧, 中间丢一个包, 后面整个 GOP 都会花屏
```

**B3 NV12 格式和 stride？**
NV12：先存亮度 Y，再存交错的颜色 UV，每 2×2 个像素共用一组颜色，大小是宽 × 高 × 1.5。stride：硬件要求内存对齐，一行实际占的字节数可能比宽度大，高度也会对齐：

```
 1920x1080 的帧, MPP 输出 hor_stride=1920, ver_stride=1088 (高按 16 对齐)

 addr 0
 +-------------------- hor_stride (1920) --------------------+
 | Y Y Y Y ... (width=1920 有效)                               |  \
 | ...                                                         |   | height = 1080 行有效
 | ...                                                         |  /
 |- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -|  \ 8 行填充 (1080..1087)
 +-------------------------------------------------------------+  /
 addr = hor_stride * ver_stride   (= 1920*1088, 不是 1920*1080 !)
 | U V U V ... (交错, 每 2x2 像素共享一对 UV)                  |  height/2 = 540 行
 +-------------------------------------------------------------+
```

**B4 什么是零拷贝？**

```
 RGA 路径(默认):
   MPP DRM buffer --(fd, DMA-BUF)--> RGA imcvtcolor(NV12 -> BGR888) --> cv::Mat(BGR)
   CPU 不碰像素, 零拷贝读取

 CPU 回退路径:
   MPP buffer --逐行 memcpy 去 stride--> 连续 NV12(yuv_) --cv::cvtColor(YUV2BGR_NV12)--> cv::Mat(BGR)

 RGA 返回错误(对齐不满足、>4G 内存等) -> 打一次 warning -> 本路永久改用 CPU 路径
```

MPP 解码出的图像在硬件内存里，有一个文件描述符（fd），直接把 fd 交给 RGA，RGA 直接读这块内存，CPU 不搬数据。

**B5 MPP 解码流程？**

```
 创建解码器 -> 送入一帧压缩数据 -> 取出解码好的图像 -> 用完马上归还缓冲区 -> 下一帧
                                     |
                                     +-- 第一帧先收到"需要多大缓冲区"的通知 (info_change),
                                         按这个大小分配一组缓冲区交给解码器, 并限制数量
```

限制数量是为了下游卡住时内存不会无限增长；用完不还，解码器就卡住了。

### C. 推理与融合

**C1 NPU 三个核怎么用起来的？**
第一个实例加载模型，其余实例用 `rknn_dup_context` **共享权重**；用 `rknn_set_core_mask` 把实例轮流绑到三个核上；多路推理线程各借一个实例，就能同时在三个核上跑。

**C2 预处理和后处理做了什么？**

```
 原图 1280x720  --->  模型输入 640x640
   scale = min(640/1280, 640/720) = 0.5
   new = 640 x 360,  pad_top = (640-360)/2 = 140 (取偶数, 满足 RGA 对齐)

   +------------------------------+
   |  gray 114   (pad_top = 140)  |
   +------------------------------+
   |                              |
   |   resized image 640 x 360    |   <- RGA improcess 一次完成: 缩放 + BGR->RGB + 写入 ROI
   |                              |
   +------------------------------+
   |  gray 114   (140)            |
   +------------------------------+

 模型坐标 -> 原图坐标:
   x_orig = (x_model - pad_left) / scale_x
   y_orig = (y_model - pad_top ) / scale_y      然后裁剪到 [0, 原图宽/高-1]
```

后处理：从 YOLOv5 三组输出（分别负责小、中、大目标）里算出框和分数，分数 = 有目标的概率 × 类别概率，过滤低分框，再做 NMS。

**C3 NMS 原理？你修的 bug 是什么？**

```
 按分数从高到低排序
   -> 取出分数最高的框保留
   -> 删掉和它重叠度 (IoU) 超过阈值的"同类"框
   -> 在剩下的框里重复, 直到处理完
```

```
 3 个框:   下标0 = 人 0.6    下标1 = 车 0.9    下标2 = 人 0.8
 排序后:   处理顺序 = [1, 2, 0]      <- 里面存的是"原始下标"

 原代码:   查类别时用的是"排序后的位置", 而不是"原始下标"   -> 查到的是别的框的类别
           删框时也没检查候选框是不是同一类
 后果:     车框把人框删掉 (跨类别误删); 同类的重复框反而没删干净

 修复:     统一先换算成原始下标再查; 只有同一类的框才互相比较 IoU
```

另外原代码的类别名是全局数组，多线程同时初始化会竞争，我改成每个模型自己持有一份。

**C4 为什么要多模型融合？怎么融合？**
- **为什么**：单个模型会漏检、误检。多个模型可以互补（通用模型找人，专用模型找安全帽），可以互相核对减少误报，也可以互相兜底减少漏报。
- **代价**：NPU 工作量翻倍。
- **注意**：代码支持多模型，默认只配了一个模型。

```
 输入: g1 (model0 的框), g2 (model1 的框), ...
  1. 展平所有框, 过滤 score < score_thresh
  2. 按 score * weight 降序排序
  3. 贪心关联: 对每个框, 找 IoU 最大且 > iou_thresh 的"同类簇"
       - 同一个簇里, 每个模型最多贡献一个框 (用 bitmask 记录)
       - 找不到就新建簇
  4. 簇内融合 (method):
       weighted   : WBF 加权框融合
       confidence : 取最高分框, 置信度 noisy-OR
       nms        : 只保留最高分框
  5. 投票: 簇大小(votes) < min_votes 的丢弃
  6. 融合结果再 applyNMS, 去掉相邻簇之间的残留重叠
```

```
   model0: A1 person 0.90   A2 car 0.70
   model1: B1 person 0.80 (与 A1 IoU=0.8)   B2 person 0.40 (与 A1 IoU=0.6)

   排序: A1(0.90) B1(0.80) A2(0.70) B2(0.40)
   A1 -> 新簇 C1 {A1}                      mask=01
   B1 -> 与 C1 IoU 0.8 > 0.55, model1 未在 C1 -> 加入 C1 {A1,B1}  mask=11
   A2 -> car, 无同类簇 -> 新簇 C2 {A2}
   B2 -> 与 C1 IoU 0.6, 但 model1 已在 C1 -> 不能加入 -> 新簇 C3 {B2}
          (同一模型的两个框必然是两个目标, 模型内部已经 NMS 过)

   min_votes=1: 输出 C1(2/2), C2(1/2), C3(1/2)
   min_votes=2: 只输出 C1
```

**C5 跳帧推理有什么副作用？**

```
 frame:   F1    F2    F3    F4    F5    F6
 infer:   [NPU]       [NPU]       [NPU]
 draw:    R1    R1    R3    R3    R5    R5          <- 显示帧率 = 输入帧率, NPU 只干一半的活
```

中间帧用的是旧的框，目标运动快时框会滞后。所以复用结果有时效（超过 0.5 秒就不画）。更好的办法是中间帧用跟踪算法预测框的位置。

### D. 推流与 GB28181

**D1 RTMP 和 RTSP 的区别？**
- RTMP：基于 TCP，FLV 封装，常推给直播服务器，延迟 1~3 秒；
- RTSP：常用于监控摄像头，视频走 RTP，可以选 TCP 或 UDP，延迟更低；
- UDP 快但可能丢包，TCP 可靠但网络差时卡顿明显。

**D2 推流线程的流程？为什么要等关键帧再连接？**

```
 按推流帧率循环:
   |
   +-- 国标没人点播?  -> 跳过, 不编码
   +-- 断线后还在等待重连?  -> 跳过
   |
   +-- 取拼接好的最新画面 -> 拷贝一份 -> 叠加时间和统计信息   (原画面别的线程也在用, 不能直接改)
   +-- 编码成 H.264
   |
   +-- 还没连上服务器?
   |     +-- 不是关键帧 -> 丢掉, 请编码器下一帧出关键帧
   |     +-- 是关键帧   -> 带上 SPS/PPS 去连接 -> 失败就等一会儿再试 (等待时间翻倍)
   |
   +-- 发送失败? -> 关闭连接 -> 等一会儿重连 -> 重连后第一帧强制关键帧
```

对方收到的第一帧必须是关键帧才能解码，否则会黑屏或花屏；关键帧前还要带 SPS/PPS，中途接入的观众才能看：

```
 编码输出:   P  P  P  I(SPS PPS IDR)  P  P ...
 未连接时:   x  x  x  |-> open(extradata=SPS/PPS) -> write(I) -> write(P) ...
             非关键帧直接丢, 并 requestKeyframe(), 让下一帧就是 I 帧

 finalizePacket(): 每个关键帧都检查是否带 SPS(7)/PPS(8) NAL, 没带就把缓存的 header 插到前面
   -> RTSP 客户端中途接入、GB28181 的 PS 流 都依赖带内参数集才能解码
```

**D3 SIGPIPE 是什么？**
往已经断开的 TCP 连接写数据，内核会发 SIGPIPE，默认直接杀死进程，而且没有任何日志。推流服务器一重启，程序就"无声无息地退出"。解决：忽略 SIGPIPE，让写操作返回错误，由程序自己重连。

**D4 断线怎么重连？为什么等待时间要翻倍？**
- 先关闭旧连接，再等一会儿重连，等待时间逐次翻倍（拉流从 0.5 秒开始，推流从 1 秒开始），有上限；连上后重置。
- 翻倍的原因：服务器长时间不可用时避免疯狂重试；很多设备同时断线时，也不会在服务器恢复瞬间一起涌上去。
- 先关旧连接的原因：避免服务器上残留旧会话，导致新连接被当成重复推流而拒绝。

**D5 GB28181 是什么？流程是什么？**
- **是什么**：国内视频监控联网的国家标准，公安、政府类项目要求设备都能接入国标平台。
- **和 RTMP/RTSP 的区别**：设备先去平台注册，**等平台点播才发视频**。
- **两部分**：信令用 SIP 协议（注册、心跳、点播、挂断）；媒体是 H.264 打包成 PS 格式，再用 RTP 通过 UDP 或 TCP 发送。

流程（最好能在纸上画出来）：

```
 设备                                          平台
  |--- 注册: 我是某某设备 ------------------------>|
  |<-- 请先认证 (给一个随机数) ---------------------|
  |--- 用密码和随机数算出的结果 (MD5 摘要) -------->|
  |<-- 注册成功 ------------------------------------|
  |--- 心跳: 我还在线 (每 60 秒) ------------------>|
  |<-- 点播: 把画面发到这个 IP:端口, 流编号 SSRC --|
  |--- 同意 --------------------------------------->|
  |<-- 确认 ----------------------------------------|
  |=== 视频数据: H.264 打包成 PS, 再切成 RTP 包 ===>|
  |<-- 挂断: 不看了 --------------------------------|
```

**D6 国标里有哪些要注意的点？**
- **SSRC** 必须用平台点播时给的值，平台靠它认出是哪一路流；
- **心跳**连续几次没回应，就认为平台掉线，重新注册；
- **重复点播**：平台重发同一个请求时原样回复，不开第二路视频；推流中来了新点播，替换旧的或拒绝新的（可配置）；
- **端口**被占用就换一个；
- **没人点播时不编码**，节省资源。

**国标要掌握到什么程度**：
- 投普通 Linux 应用岗：会 D5、D6 就够了，能画出注册和点播流程；
- 岗位写了安防、国标：再了解 MD5 摘要认证大致怎么算、PS 包的大致结构、TCP 模式下谁主动连接（见学习指南第 9 章）；
- 不用背协议细节。

### E. 调试

**E1 内存泄漏怎么查？**

```
 RSS 持续增长?
   |
   +-- 否, 涨到一定程度后稳定
   |     -> 不是泄漏: 分配器缓存 / 内存碎片 / 各级缓冲填满
   |        (glibc 每线程 arena 会缓存内存: 可试 MALLOC_ARENA_MAX=2 或定期 malloc_trim(0) 验证)
   |
   +-- 是, 随运行时间线性增长
         |
         +-- /proc/<pid>/fd 数量也在涨?     -> 句柄泄漏 (socket / avformat / 文件未关闭)
         +-- Threads 数量在涨?              -> 线程泄漏 (线程未 join / 不断新建)
         +-- CMA / dma_buf 在涨, 堆没涨?     -> 硬件内存泄漏 (MPP/RGA/RKNN buffer 未释放)
         +-- 普通堆在涨                      -> ASan/LSan / heaptrack / massif 找分配点
```

- **普通内存**：用 ASan（编译加 `-fsanitize=address`，正常退出时打印泄漏位置）、heaptrack、valgrind；
- **硬件内存**：MPP/NPU 的缓冲区 ASan 查不到，要看系统的 CMA 用量，并检查每个"申请"都有对应的"释放"。例如 `rknn_outputs_get` 之后必须 `rknn_outputs_release`，漏了每帧泄漏约 2MB；
- **缩小范围**：逐个关掉模块（关推流、关显示、只留一路），看关掉哪个之后泄漏消失。

**E2 程序卡死怎么查？**
`gdb -p 进程号`，`thread apply all bt` 看每个线程卡在哪：等锁、等条件变量，还是等网络。退出时卡死，最常见的原因是有缓冲区没关闭，线程还在等。

**E3 程序崩溃怎么查？**
打开 core dump，用 gdb 看崩溃时的调用栈；越界、重复释放用 ASan 复现。进程没有任何日志就消失了，先怀疑 SIGPIPE 和系统内存不足被杀（OOM）。

**E4 性能瓶颈怎么定位？**

```
 现象                                   结论
 ------------------------------------  --------------------------------------------
 chN.drop.pkt 持续增长                  解码跟不上 -> 看 chN.decode / chN.yuv2bgr 负载
 chN.drop.frame 持续增长                推理跟不上 -> 看 chN.infer / <model>.npu / <model>.wait
 <model>.wait 平均耗时大                实例不够, 大家在排队抢实例 -> 增加 instances
 <model>.pre 很大                       RGA 失败回退到了 CPU? 日志里找 "rga ... fallback"
 pushN.encode 很大                      MPP 编码没启用(回退 libx264)? 看启动日志的编码器名
 mosaic.compose 很大                    拼接用了 CPU 缩放, 或拼接分辨率过高
 某阶段 load 接近 100%                  该线程已饱和, 它就是瓶颈
```

再配合 `top -H` 看每个线程的 CPU、看 NPU 三个核的占用。测试前先用 `performance.sh` 定频，减少误差。

## 4. 基础知识（和项目挂钩）

**条件变量为什么要用 while（或带条件的 wait）？**
线程可能在没人通知时醒来（虚假唤醒），也可能醒来时条件已被别的线程改掉，所以醒来后要重新检查。项目里所有等待都是带条件、带超时的写法。

**notify_one 和 notify_all？**
多了一个数据，叫醒一个就够（notify_one）；关闭、停止这种全局变化，必须全叫醒（notify_all），否则有线程永远醒不来。

**死锁的四个条件？怎么避免？**
互斥、占有并等待、不可剥夺、循环等待。避免：固定加锁顺序、一次只持有一个资源、加锁带超时。项目里线程池线程数等于实例数，每个任务只借一个实例，就是破坏"占有并等待"。

**atomic 和 volatile？**
`volatile` 只保证不被编译器优化，不保证原子性，不能用来做线程同步；`atomic` 保证操作是原子的。项目里停止标志、统计计数都用 `atomic`。

**线程池原理？线程数怎么定？**
提前建好线程，从任务队列取任务执行，避免反复创建线程。计算密集型 ≈ CPU 核数；IO 密集型可以多一些；受外部资源限制时按资源数定（项目里 = 模型实例数）。

**进程和线程的区别？进程间通信有哪些？**
进程是资源分配单位，有独立的内存空间；线程是调度单位，共享进程的内存。进程间通信：管道、消息队列、共享内存（最快）、信号量、信号、socket。项目用多线程，因为各级之间要传大图像，共享内存最方便。

**select、poll、epoll 的区别？**

| | select | poll | epoll |
|---|---|---|---|
| 连接数上限 | 1024 | 无 | 无 |
| 每次调用 | 把全部连接拷进内核 | 同左 | 只注册一次 |
| 找就绪的连接 | 遍历全部 | 遍历全部 | 内核直接给出就绪的 |
| 适合 | 连接少 | 连接少 | 连接多 |

项目里国标信令只有一个连接，用 poll 足够。

**TCP 和 UDP？音视频为什么常用 UDP？**
TCP 可靠、有序，但丢包重传会卡住后面的数据；UDP 不可靠但延迟低。实时视频"宁可丢一帧也不要卡住"，所以常用 UDP；网络差或要穿透防火墙时用 TCP。

**TCP 粘包？**
TCP 是字节流，没有消息边界，要自己分：定长、分隔符、或者在前面加长度（最常用）。项目里国标 TCP 传输就是每个包前加 2 字节长度。

**信号处理函数里能做什么？**
只能做很简单的事（比如设一个标志），不能调用 `printf`、`malloc`、加锁：信号可能在主流程持有锁时到来，导致死锁。项目里退出信号只设一个原子标志。

**malloc 原理？RSS 是什么？**
小块内存从堆上分配，释放后放回空闲链表复用，不一定马上还给系统；大块内存直接向系统申请，释放时立即归还。RSS 是进程实际占用的物理内存，查泄漏主要看它的趋势（`/proc/进程号/status`）。

**智能指针？shared_ptr 线程安全吗？**
unique_ptr 独占；shared_ptr 共享（引用计数）；weak_ptr 不增加计数，用来打破循环引用。shared_ptr 的引用计数是原子的，多个线程各自拷贝没问题，但它指向的对象本身没有保护。

**RAII？**
构造时获取资源，析构时释放，出了作用域自动释放，出错也不会漏。项目里线程封装（析构时 join）、实例借用（析构时归还）都是 RAII。

## 5. 手撕代码：思路与要点

> 最常考的是前两题。先把思路和要点讲清楚，再动手写。完整实现可以参考项目源码：`include/common/BlockingQueue.hpp`（阻塞队列）、`include/common/ThreadPool.hpp`（线程池）、`src/infer/postprocess.cc`（NMS）。
> 其它常见题：LRU 缓存、简易 shared_ptr、单例、memmove、字符串处理、链表反转。

### 题 1：有界阻塞队列（生产者-消费者）

```
 生产者 push:                              消费者 pop:
   加锁                                      加锁
   等 "没满 或 已关闭"  (条件变量 not_full)    等 "不空 或 已关闭"  (条件变量 not_empty)
   已关闭? -> 返回失败                        空了且已关闭? -> 返回失败
   放入数据                                   取出数据
   叫醒一个消费者 (not_empty.notify_one)      叫醒一个生产者 (not_full.notify_one)
   解锁                                      解锁

 close(): 加锁 -> 标记关闭 -> 解锁 -> 两个条件变量都 notify_all (叫醒所有人)
```

**要点**：
- 两个条件变量，生产者和消费者各等各的，叫醒时不会叫错人；
- 等待一定带条件（防虚假唤醒）；
- 关闭时用 notify_all；
- 关闭后消费者要能把剩下的数据取完。

### 题 2：线程池

```
 构造: 创建 N 个工作线程, 每个都执行下面的循环

 工作线程循环:
   加锁 -> 等 "有任务 或 要停止" -> 要停止且没任务了? 退出
        -> 取出一个任务 -> 解锁
   执行任务 (在锁外执行!)

 submit(任务):
   把任务包进 packaged_task, 拿到它的 future (取结果的凭证)
   加锁 -> 放进任务队列 -> 解锁 -> 叫醒一个工作线程
   返回 future 给调用者

 析构: 加锁 -> 标记停止 -> 解锁 -> notify_all -> join 所有线程
```

**要点**：
- 任务在锁外执行，否则所有线程只能串行；
- `packaged_task` 会把返回值和异常都放进 future，线程本身不会因为异常而 terminate；
- 析构时要 join（否则 terminate），并决定剩余任务是做完还是丢弃。

### 题 3：两个线程交替打印 1~n

```
 共享: 一把锁, 一个条件变量, 当前数字 cur = 1
 线程A (打印奇数) / 线程B (打印偶数), 各自循环:
   加锁 -> 等 "cur > n  或  cur 的奇偶轮到我"
        -> cur > n? 退出
        -> 打印 cur, cur++ -> notify_all 叫醒对方 -> 解锁
```

**要点**：结束条件（`cur > n`）一定要写进等待条件，否则最后一个数打印完，另一个线程会永远等下去。

### 题 4：IoU + NMS（和项目相关）

```
 IoU(A, B) = 交集面积 / (A 面积 + B 面积 - 交集面积)
   交集宽 = max(0, min(A右, B右) - max(A左, B左)), 交集高同理

 NMS:
   按分数从高到低排序
   依次处理每个没被删的框:
       保留它
       把后面"同类"且和它 IoU > 阈值 的框标记为删除
```

**要点**：先排序；只删同类的框；复杂度 O(n²)；下标含义要统一（项目里原来的 bug 就是下标混用）。

## 6. 踩坑故事

> 被问"遇到过什么难题"时用。按"背景 → 问题 → 怎么定位 → 怎么解决 → 结果"讲，**重点讲定位过程**。
> ✅ 是开发中真实发生的；🛡️ 是设计时考虑到并做过测试验证的，讲的时候如实说，不要说成自己踩过的坑。

**故事 1：NMS 下标混用 ✅**
- **背景**：把单路 demo 改成多路多模型时，重新检查后处理代码。
- **问题**：发现 NMS 排序后的下标和原始下标混用，而且没检查类别。手工构造例子验证，会出现车框把人框删掉、同类重复框删不干净。
- **解决**：统一用原始下标，并按类别判断。
- **顺带**：把全局类别名数组改成每个模型自己持有，解决多线程初始化时的竞争。

**故事 2：头文件导致链接报"重复定义" ✅**
- **问题**：原来只有一个文件用线程池头文件，重构后多个文件都用，链接时报"重复定义"。
- **原因**：头文件里在类外定义了一个静态常量。C++14 里，每个包含这个头文件的源文件都会生成一份定义，违反"单一定义规则"（ODR）；以前只有一个源文件包含它，所以没暴露。
- **解决**：改成枚举常量，枚举不需要单独定义。
- **收获**：理解了 C++17 为什么引入 `inline` 变量。

**故事 3：国标视频流"偶发解码错误" ✅**

```
 现象: 模拟平台收到的 PS 流, 解码时总报一次错
   |
   v
 第 1 层: 检查每个 PS 包的结构 -> 全部正确, 封装格式没问题
   |
   v
 第 2 层: 提取出里面的 H.264 单独解码 -> 仍然报错, 问题在视频数据本身
   |
   v
 第 3 层: 二分查找第几帧出错 -> 只有最后一帧, 而且只收到了一部分
   |
   v
 结论: 测试程序在 3 秒时停止接收, 把最后一帧截断了; 封装和发送都没问题
```

**收获**：分层排查、用证据说话，测试方法本身也可能出错。

**故事 4：推流服务器重启导致进程直接退出 🛡️**
- **背景**：往已断开的连接写数据会触发 SIGPIPE，默认直接杀死进程，而且没有日志。
- **设计**：忽略 SIGPIPE；写失败时关闭旧连接、等待后重连，重连后第一帧强制关键帧。
- **验证**：用 mediamtx 做服务器，推流中途把它关掉再重启。日志显示断开、重连、恢复推流，进程没有退出。

## 7. 项目不足与改进

> 面试官常问"有什么不足"。挑 2~3 条，按"现状 → 影响 → 怎么改"来说，能主动说出缺点是加分项。

| 不足 | 怎么改 |
|---|---|

## 8. 上板要测的数据

面试一定会问"跑多少帧、延迟多少"。上板后至少测这些：

| 数据 | 怎么拿 |
|---|---|
| 每路帧率、推理耗时 | 程序日志里的性能报告（`chN.out`、`chN.infer`） |
| NPU 三个核占用 | `sudo cat /sys/kernel/debug/rknpu/load` |
| 整机和各线程 CPU | `top -H -p 进程号` |
| 端到端延迟 | 拍计时器（见 F2） |
| 内存是否稳定 | 跑几个小时，看 `/proc/进程号/status` 里的 VmRSS 是否平稳 |
| 故障恢复 | 拔一路网线、重启推流服务器，看能否自动恢复 |

同时看启动日志，确认硬件真的用上了：
- 解码器显示 `mpp`；
- 编码器显示 `mpp h264 encoder`；
- 没有 `rga ... fallback` 的警告。

**面试时这样说数字**："在 RK3588、4 路 1080p、yolov5s 的条件下，每路 xx fps，NPU 占用约 xx%，延迟约 xx 毫秒，连续运行 xx 小时内存平稳。"

条件、数字、稳定性，三样都要有。
