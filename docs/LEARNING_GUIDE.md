## 1. 项目在做什么

**一句话**：在 RK3588 上同时处理 4 路视频，用硬件解码、NPU 做目标检测，把结果拼成一个画面显示，并推流出去。

```
 4 路视频 (MP4 文件 / RTSP 摄像头)
      |
      v
 s1 拉流    FFmpeg 读出压缩数据 (H.264/H.265)
      |     有界队列
      v
 s2 解码    MPP 硬件解码 -> NV12 图像
      |
      v
 s3 转换    RGA 硬件转成 BGR 图像
      |     最新帧缓冲
      v
 s4 推理    NPU 跑 YOLOv5 检测 (可以多个模型, 3 个 NPU 核并行)
      |
      v
 s5 融合    多个模型的检测框合并成一份, 画框
      |     最新帧缓冲
      v
 s6 输出    4 路拼成 2x2 画面 -> 本地显示 / 编码推流 (RTMP / RTSP / GB28181)
```

**用到的技术**

| 技术 | 作用 |
|---|---|
| FFmpeg | 拉流（读 RTSP/文件）、推流（RTMP/RTSP） |
| MPP | Rockchip 的硬件视频编解码 |
| RGA | Rockchip 的硬件 2D 图像处理（颜色转换、缩放） |
| RKNN | Rockchip 的 NPU 推理库 |
| OpenCV | 画框、显示；硬件不可用时做软件兜底 |
| C++ 多线程 | 线程、互斥锁、条件变量、原子变量、线程池 |

## 2. 线程模型

```
 ch0: [拉流线程] -> 队列 -> [解码线程] -> 最新帧 -> [推理线程] --+
 ch1: [拉流线程] -> 队列 -> [解码线程] -> 最新帧 -> [推理线程] --+     模型实例池
 ch2: [拉流线程] -> 队列 -> [解码线程] -> 最新帧 -> [推理线程] --+-->  实例0 @ NPU核0
 ch3: [拉流线程] -> 队列 -> [解码线程] -> 最新帧 -> [推理线程] --+     实例1 @ NPU核1
                                                        |               实例2 @ NPU核2
                                                        v
                                 各路结果 -> [拼接线程] -> 主线程显示 / [推流线程] -> 网络
```

| 线程 | 数量 | 做什么 |
|---|---|---|
| 拉流 | 每路 1 | 读网络/文件，断了自动重连 |
| 解码 | 每路 1 | 硬件解码，转成 BGR |
| 推理 | 每路 1 | 控制帧率、调用 NPU、融合、画框 |
| 推理线程池 | 多模型时才用 | 同一帧的多个模型同时跑 |
| 拼接 | 1 | 按固定帧率把各路结果拼成一个画面 |
| 推流 | 每个推流目标 1 | 编码 + 发送；GB28181 还多一个信令线程 |
| 主线程 | 1 | 处理退出信号、显示窗口 |

**关键点**：每一路是一条独立的流水线，4 路同时跑，互不等待。4 个推理线程共享 NPU。

## 3. 核心原理

### 3.1 生产者-消费者：两种缓冲区

上一级生产数据、下一级消费数据，中间放一个缓冲区，两边就可以按各自的速度工作。项目里用了两种缓冲区：

| | 有界队列 | 最新帧缓冲 |
|---|---|---|
| 放在哪 | 拉流 → 解码 | 解码 → 推理 → 输出 |
| 放的什么 | 压缩后的视频数据（几 KB 一帧） | 解码后的图像（几 MB 一帧） |
| 满了怎么办 | 文件：等下游消费（背压）<br>实时流：丢掉积压的一整组画面 | 新帧直接覆盖旧帧 |
| 为什么 | 压缩数据前后依赖，不能随便丢 | 只要最新的一帧，延迟不会越积越多 |

一句话记住：**码流不能随便丢，图像只要最新的。**

实现上，两种缓冲区都是"互斥锁 + 条件变量"：
- 互斥锁保护数据，同一时刻只有一个线程能改；
- 条件变量让等待的线程睡眠，数据来了再叫醒它，不浪费 CPU；
- 醒来后要重新检查条件（防止虚假唤醒）；
- 等待都带超时，或者能被 `close()` 叫醒，保证退出时不会卡住。

代码：`include/common/BlockingQueue.hpp`、`include/common/Mbuffer.hpp`

### 3.2 资源竞争：模型实例池

**竞争在哪**：4 个推理线程，但 NPU 只有 3 个核；同一个模型实例（`rknn_context`）同一时刻只能被一个线程使用。

**怎么解决**：做一个"实例池"，像借东西一样：

```
 空闲列表: [实例0(核0), 实例1(核1), 实例2(核2)]    <- 用一把锁保护

 借: 加锁 -> 有空闲就拿走一个, 没有就睡着等 -> 解锁
 用: 用这个实例推理 (此时只有我在用)
 还: 加锁 -> 放回列表 -> 叫醒一个在等的线程 -> 解锁
```

"还"写在析构函数里（RAII），就算中途出错也一定会还。

- **路和路之间**：没有固定顺序，谁先借到谁先算。
- **同一路内部**：一定按时间顺序。一个推理线程算完一帧才拿下一帧，处理不过来就跳过中间帧、直接拿最新的。

代码：`src/infer/ModelManager.cc`（`Lease`）

### 3.3 线程池：只在多模型时用

**线程池**就是提前建好几个线程，守着一个任务队列：有任务就取出来执行，执行完把结果放进 `future`（相当于取餐凭证），提交任务的人凭它等结果。

在项目里：
- **单模型**：不用线程池，推理线程自己借实例、自己推理。
- **多模型**：同一帧要跑 A、B 两个模型。推理线程把两个任务丢进线程池，两个模型在不同 NPU 核上同时算，再用两个 `future` 等结果，最后融合。这样一帧只需要一个模型的时间，而不是两个模型相加。

**为什么不会死锁**：线程池的线程数 = 模型实例总数。每个任务只借一个实例，借到后一定能算完、归还，不会出现"拿着一个又等另一个"的情况。

### 3.4 三层并行

1. **路级**：4 条流水线同时跑。
2. **模型级**：同一帧的多个模型同时跑（线程池）。
3. **硬件级**：实例绑在 3 个不同的 NPU 核上，真正同时计算。

**限制**：NPU 只有 3 个核，同一时刻最多 3 个推理在算，多出来的在排队。所以多模型能降低单帧延迟，但总工作量会翻倍。

### 3.5 实时性：每一级都要有丢帧策略

实时视频的原则是**宁可丢帧，不能延迟**。项目里每一级都有明确的丢法，并且丢了多少都会统计：

| 位置 | 丢法 | 统计项 |
|---|---|---|
| 拉流 | 队列满了丢掉整组画面，等下一个关键帧 | `drop.pkt` |
| 解码后 | 推理没来得及取，新帧覆盖旧帧 | `drop.frame` |
| 推理前 | 超过目标帧率的帧直接丢 | `drop.fps` |
| 推理 | 每 N 帧推理一次，中间帧复用上次的框（跳帧推理） | `reuse` |

**目标帧率控制的原理**：按"绝对时间点"来算下一帧什么时候处理（下一帧时间 += 周期），而不是每次睡固定时长，这样误差不会越积越多；处理慢了就重新对齐，不去"追帧"。

### 3.6 线程安全退出

`std::thread` 有两个坑：
1. 线程对象析构时如果还没 `join`，程序直接调用 `std::terminate` 崩溃；
2. 线程里抛出没被捕获的异常，也会 `terminate`。

项目的做法：
- 用 `WorkerThread` 封装线程：析构时自动 `join`，线程入口统一捕获异常；
- 退出信号处理函数里只设置一个原子标志，主循环看到后走正常退出流程；
- 忽略 `SIGPIPE`：推流时对方断开连接，继续写数据会触发这个信号，默认会直接杀死进程。

退出和启动的具体顺序见第 5 节。

## 4. 各环节的原理与流程

### 4.1 拉流（StreamLoader）

**流程**：打开输入 → 循环读包 → 格式转换 → 放进队列；出错就关闭，等一会儿再重连。

```
 连接中 --成功--> 读包中 --出错/超时--> 等待重连(0.5s, 1s, 2s ... 逐次翻倍, 有上限) --> 连接中
                     |
                     +-- 文件读完: 循环播放则回到开头, 否则结束
```

要掌握的原理：
- **超时**：网络断了，FFmpeg 的读取可能卡很久。给它注册一个回调，每次读之前设一个截止时间，超时就让它立即返回，然后重连。
- **重连为什么要逐次翻倍等待**：服务器长时间不可用时，不会疯狂重试浪费资源；很多设备同时重连时，也不会一起涌上去。
- **格式转换**：MP4 文件里的 H.264 用"长度 + 数据"的格式（AVCC），硬件解码器要"起始码 + 数据"的格式（Annex-B），所以要用 FFmpeg 的 `h264_mp4toannexb` 转一下。
- **为什么丢要丢到关键帧**：
  - I 帧（关键帧）自己就能解码；P 帧要参考前面的帧。
  - 中间丢一个包，后面的帧都会花屏，直到下一个关键帧。
  - 所以队列满了，就把积压的整组清掉，从下一个关键帧重新开始。

代码：`src/stream/StreamLoader.cc`

### 4.2 解码（MPP）

**流程**：

```
 创建解码器 -> 送入一帧压缩数据 -> 取出解码好的图像 -> 用完马上归还缓冲区 -> 下一帧
                                     |
                                     +-- 第一帧会先收到"需要多大缓冲区"的通知,
                                         按这个大小分配一组缓冲区交给解码器(限制数量)
```

要掌握的原理：
- **缓冲区为什么要限制数量、用完马上归还**：解码器的输出缓冲区是一个池子，用完不还，解码器就卡住了；限制数量，是为了防止下游卡住时内存无限增长。
- **NV12 格式**：先是一整块亮度（Y），后面是颜色（UV）交错存放，每 4 个像素共用一组颜色，大小是宽 × 高 × 1.5。人眼对亮度敏感、对颜色不敏感，所以视频都这样压缩颜色。
- **stride（行跨度）**：硬件要求内存对齐，一行实际占的字节数可能比图像宽度大，高度也会对齐（1080 对齐成 1088）。

```
 +-------- stride (1920) --------+
 | Y 数据 1080 行                  |
 | 填充 8 行                       |   <- 高度对齐到 1088
 +-------------------------------+   <- 颜色数据从这里开始 (stride x 1088), 不是 1920 x 1080
 | UV 数据 540 行                  |
 +-------------------------------+
```

  按宽 × 高去找颜色数据的位置，画面会发绿，这是 Rockchip 平台的经典坑。
- **兜底**：MPP 不可用时自动改用 FFmpeg 软件解码。

代码：`src/decode/MppDecoder.cc`

### 4.3 颜色转换（RGA）

- **零拷贝**：MPP 解码出来的图像在一块硬件内存里，这块内存有一个文件描述符（fd）。把 fd 直接交给 RGA，RGA 直接读这块内存做转换，CPU 不用搬数据。
- **兜底**：RGA 失败（尺寸对齐不满足等）就改用 OpenCV 的 `cvtColor`，只打一次警告。

代码：`src/decode/DecodeWorker.cc`（`mpp_decoder_cb`）

### 4.4 推理（RKNN）

**流程**：预处理 → NPU 推理 → 后处理。

**1. 预处理（letterbox）**：图像等比缩放到 640×640，多出来的地方填灰边。这样和训练时一致，比直接拉伸准。

```
 1280x720 原图 -> 缩放一半 -> 640x360, 上下各补 140 行灰边 -> 640x640
 检测框换算回原图:  x原图 = (x模型 - 左边灰边) / 缩放比例
```

**2. 多实例和绑核**：
- 第一个实例加载模型，其余实例用 `rknn_dup_context` **共享权重**（不重复占内存）；
- 用 `rknn_set_core_mask` 把实例轮流绑到 3 个 NPU 核上，负载均衡。

**3. 后处理**：
- YOLOv5 输出三组不同尺寸的特征图（80×80、40×40、20×20），分别负责小、中、大目标；
- 每个格子算出框和分数，分数 = 有目标的概率 × 类别概率，低于阈值的丢掉；
- 最后做 NMS 去重。

**4. NMS（非极大值抑制）**：同一个目标往往被框出好几个框，要去重。

```
 按分数从高到低排序
 循环: 取出分数最高的框保留 -> 删掉和它重叠度(IoU)超过阈值的"同类"框 -> 继续
```

原代码的 NMS 有一个 bug：排序后的下标和原始下标混用，而且没检查类别，会出现"车框把人框删掉"。已经修复。

代码：`src/infer/rknn_lite.cc`、`src/infer/postprocess.cc`

### 4.5 多模型融合

**为什么融合**：单个模型会漏检、误检。多个模型可以：
- **互补**：通用模型找人，专用模型找安全帽；
- **互相核对**：几个模型都认同才算，误报更少；
- **互相兜底**：任一模型看到就保留，漏报更少。

**流程**：

```
 1. 把所有模型的框放在一起, 按分数排序
 2. 关联: 同类、重叠度超过阈值的框, 认为是同一个目标, 分到一组 (每组里每个模型最多一个框)
 3. 合并: 每组合成一个框 (按分数加权平均位置)
 4. 投票: 组里检出的模型数不够 min_votes 的丢掉
          min_votes=1 -> 任一模型检出就留 (漏报少)
          min_votes=模型数 -> 全部检出才留 (误报少)
 5. 最后再做一次 NMS 去重
```

**代价**：NPU 工作量翻倍。

**现状**：代码支持多模型，但默认只配置了一个模型，这时融合基本等于直接输出。

代码：`src/fusion/DetectionFusion.cc`

### 4.6 拼接和推流

**拼接**：拼接线程按固定帧率，去各路取最新的结果画面，拼成 2×2。

它是主动"拉"，而不是等各路"推"过来。所以某一路卡住，也不会拖慢整个画面，那一格会显示"重连中"。

**推流流程**：

```
 取最新画面 -> 拷贝一份再叠加时间和统计信息 -> 硬件编码成 H.264
   -> 还没连接? 等到关键帧再连接 -> 发送
   -> 发送失败? 关闭旧连接 -> 等待(逐次翻倍) -> 重连 -> 第一帧强制关键帧
```

要掌握的原理：
- **为什么要拷贝再叠加**：原画面被拼接线程、推流线程同时读取，直接在上面画会影响别人。
- **为什么等关键帧再连接**：对方收到的第一帧必须是关键帧才能解码。另外，关键帧前要带上 SPS/PPS（描述分辨率等解码参数的信息），中途接入的观众才能看。
- **RTMP 和 RTSP**：
  - RTMP 用 FLV 格式封装，常推给直播服务器，延迟 1~3 秒；
  - RTSP 常用于监控，视频走 RTP，可以选 TCP 或 UDP，延迟更低。
- **SIGPIPE**：往已断开的连接写数据会触发 SIGPIPE，默认直接杀死进程。所以要忽略它，让写操作返回错误，由程序自己去重连。

代码：`src/output/Compositor.cc`、`src/output/StreamingMgr.cc`

### 4.7 GB28181 国标接入

**是什么**：国内视频监控联网的国家标准。公安、政府类项目，要求所有摄像头都能接入同一个"国标平台"，统一管理、统一看画面。

**和 RTMP/RTSP 的区别**：RTMP/RTSP 是一开机就推流；GB28181 是设备先去平台报到，**等平台点播才发视频**。

**流程**（像员工打卡）：

```
 设备                                          平台
  |--- 注册: 我是某某设备 ------------------------>|
  |<-- 请先认证 (给一个随机数) ---------------------|
  |--- 用密码和随机数算出的结果 (MD5 摘要) -------->|
  |<-- 注册成功 ------------------------------------|
  |--- 心跳: 我还在线 (每 60 秒) ------------------>|
  |<-- 点播: 把画面发到这个 IP:端口, 流编号 SSRC --|
  |--- 同意 --------------------------------------->|
  |<-- 确认 ----------------------------------------|
  |=== 视频数据: H.264 打包成 PS, 再切成 RTP 包 ===>|
  |<-- 挂断: 不看了 --------------------------------|
```

要掌握的原理：
- **两部分**：
  - 信令用 SIP 协议（原本是网络电话协议），负责注册、心跳、点播、挂断；
  - 媒体是视频数据，先打包成 PS 格式，再用 RTP 分成小包，通过 UDP 或 TCP 发送。
- **SSRC**：平台点播时指定的流编号，设备发的每个 RTP 包都要带上它，平台靠它认出是哪一路流。填错了，平台收到也不认。
- **心跳的作用**：让平台知道设备还在线。设备连续几次没收到回应，就认为平台掉线，重新注册。
- **项目里处理的异常情况**：
  - 端口被占用就换一个；
  - 平台重复发同一个点播请求，原样回复，不开第二路视频；
  - 推流中又来新的点播，替换掉旧的，或者拒绝新的（可配置）；
  - 没人点播时不编码。

代码：`src/output/Gb28181Sink.cc`

## 5. 启动与退出顺序

```
 启动:  加载模型 -> 创建各级缓冲区 -> 启动推流 -> 拼接 -> 推理 -> 解码 -> 拉流
        (最容易失败的先做)              (消费者先就绪, 生产者最后启动)

 退出:  1. 通知所有线程停止, 并关闭所有缓冲区 (把正在等待的线程全部叫醒)
        2. 按 拉流 -> 解码 -> 推理 -> 拼接 -> 推流 的顺序等线程结束
        3. 最后释放 NPU 资源 (确保已经没有线程在用)
```

**为什么这样排**：
- 先加载模型：模型加载最容易失败（路径错、驱动不匹配），失败时还没有启动任何线程和网络连接，直接退出很干净。
- 消费者先启动：第一帧到来时，下游都已经准备好了。
- 退出时先关闭缓冲区：不这样做，等在缓冲区上的线程永远醒不过来，程序就卡住退不出。
- NPU 最后释放：如果先释放，还在推理的线程会崩溃。

## 6. 调试思路

### 6.1 性能瓶颈怎么找

1. **看程序自带的性能报告**：每隔几秒打印一次，列出每个阶段每秒处理多少次、平均耗时多少、负载多少（负载 = 每秒次数 × 平均耗时，接近 100% 说明这一级已经满负荷）。
2. **看丢帧统计**：
   - `drop.pkt` 增长：解码跟不上；
   - `drop.frame` 增长：推理跟不上；
   - 模型的 `wait` 耗时大：实例不够，大家在排队抢。
3. **看硬件占用**：
   - `top -H` 看每个线程的 CPU（线程都起了名字）；
   - `/sys/kernel/debug/rknpu/load` 看 3 个 NPU 核各自的占用。

**口诀**：看哪一级开始丢帧，瓶颈就在它的下游。

### 6.2 内存泄漏怎么查

```
 内存(RSS)是不是一直在涨?
   |
   +-- 涨到一定程度就不涨了 -> 不是泄漏 (缓冲区填满、内存分配器缓存)
   |
   +-- 一直线性上涨 -> 是泄漏, 再分类:
         +-- 打开的文件/连接数也在涨 -> 连接没关 (重连时没关旧连接)
         +-- 线程数在涨              -> 线程没回收
         +-- 硬件内存(CMA)在涨       -> MPP / NPU 的缓冲区没释放
         +-- 普通内存在涨            -> 用 ASan 找到是哪一行分配的
```

**常用工具**：
- **ASan**：编译时加 `-fsanitize=address`，程序正常退出时会打印泄漏的位置，同时还能查越界、释放后使用；
- **valgrind / heaptrack**：不用重新编译，但更慢。

**硬件内存要单独看**：MPP 解码缓冲区、NPU 内存不是 `malloc` 分配的，ASan 查不到，只能：
- 看系统的 CMA 可用量（`/proc/meminfo`）有没有持续下降；
- 检查每个"申请"都有对应的"释放"。例如：
  - 解码出来的帧要 `mpp_frame_deinit`；
  - `rknn_outputs_get` 之后要 `rknn_outputs_release`，漏掉的话每帧泄漏约 2MB。

**缩小范围**：只改配置，逐个关掉模块（关推流、关显示、只留一路……），看关掉哪个之后泄漏消失。

### 6.3 程序卡死、崩溃怎么查

- **卡死**：`gdb -p <进程号>`，输入 `thread apply all bt` 看每个线程卡在哪一行，等锁的、等条件变量的、等网络的一眼就能看出来。
- **崩溃**：打开 core dump（`ulimit -c unlimited`），崩溃后用 `gdb 程序 core文件` 看调用栈；越界、重复释放这类问题用 ASan 复现最快。
- **进程无声无息消失、也没有日志**：优先怀疑两个原因：
  - SIGPIPE 没忽略；
  - 被系统的 OOM killer 杀了（`dmesg | grep -i oom` 查看）。
- **多线程数据竞争**：用 ThreadSanitizer（`-fsanitize=thread`）。注意 FFmpeg、OpenCV 内部的引用计数会产生误报，要看报告里冲突的两边是不是都在第三方库里。

### 6.4 常见问题速查

| 现象 | 原因 | 解决 |
|---|---|---|
| 画面发绿、颜色错位 | 颜色数据位置按宽 × 高算了，没按 stride | 按 stride 计算 |
| 人脸发蓝 | RGB 和 BGR 搞反了 | OpenCV 默认是 BGR |
| 检测框整体偏移 | 灰边和缩放比例没有换算回去 | x = (x模型 − 灰边) / 缩放比例 |
| 延迟越来越大 | 实时流用了会排队的缓冲区 | 实时流丢 GOP，图像只留最新帧 |
| 一段时间花屏 | 随便丢了 P 帧 | 丢到下一个关键帧为止 |
| 推流端黑屏很久才出画面 | 第一帧不是关键帧 | 等关键帧再发，关键帧前带 SPS/PPS |
| 推流断开后进程没了 | SIGPIPE | 忽略 SIGPIPE |
| 退出时卡住 | 有缓冲区没关闭，线程还在等 | 退出时先关闭所有缓冲区 |
| 退出时 terminate | 线程对象析构前没有 join | 析构时 join |
| 国标平台注册上了但没画面 | SSRC 不对、传输方式不匹配 | 抓包对照平台发来的点播信息 |
